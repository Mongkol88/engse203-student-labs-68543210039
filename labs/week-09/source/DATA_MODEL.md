## 1. ภาพรวม

### แผนภาพความสัมพันธ์

```text
┌──────────────────────────────┐          ┌───────────────────────────────────┐
│            users             │          │             requests              │
├──────────────────────────────┤          ├───────────────────────────────────┤
│ PK  id          INTEGER      │ 1      N │ PK  id           TEXT             │
│     name        TEXT         ├──────────┤ FK  requester_id INTEGER          │
│     department  TEXT         │          │     request_type TEXT             │
│     email       TEXT UNIQUE  │          │     location     TEXT             │
└──────────────────────────────┘          │     details      TEXT             │
                                          │     priority     TEXT             │
                                          │     status       TEXT             │
                                          │     created_at   TEXT             │
                                          └───────────────────────────────────┘
```

### รูปแบบความสัมพันธ์ (Relationship)

ความสัมพันธ์ระหว่างตาราง `users` และ `requests` เป็นแบบ **One-to-Many**

* ผู้ใช้ 1 คน สามารถสร้างคำร้อง ได้หลายรายการ
* คำร้อง 1 รายการ จะต้องมาจากผู้ใช้ที่ระบุตัวตนได้เพียง 1 คนเท่านั้น โดยเชื่อมโยงผ่าน `requests.requester_id` ชี้ไปยัง `users.id`

## 2. ทำไมต้องแยกเป็น 2 ตาราง

ใน Week 06–07 ระบบเก็บข้อมูลแบบตารางเดียว โดยเก็บชื่อผู้แจ้ง `requesterName` และข้อมูลอื่น ๆ รวมอยู่ในคำร้องแต่ละรายการ ซึ่งส่งผลให้เกิดปัญหาสำคัญของฐานข้อมูล

* เมื่อแยกตารางเป็น `users` และ `requests` ข้อมูลชื่อสมชายจะถูกเก็บไว้ที่ตาราง `users` เพียงที่เดียว หากมีการเปลี่ยนชื่อ ก็แก้ไขเพียง **1 จุดเท่านั้น** และทุกคำร้องที่อ้างอิง `requester_id` เดิมจะเห็นชื่อใหม่ที่ถูกต้องทันที
* ในระบบเดิม หากสมชายแจ้งคำร้องไว้ 50 รายการ เมื่อสมชายเปลี่ยนชื่อ เราจำเป็นต้องสั่ง `UPDATE` ข้อมูลทุกแถวทั้ง 50 รายการ หากมีคำสั่งตกหล่นหรือระบบขัดข้องระหว่างทาง จะทำให้ชื่อของผู้ใช้คนเดียวกันไม่ตรงกันในแต่ละคำร้อง

## 3. รายละเอียดตาราง

### ตาราง `users`

| :------------- | :------------------- | :------------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`           | INTEGER              | PRIMARY KEY AUTOINCREMENT | ใช้เป็น Surrogate Key ตัวเลขรันอัตโนมัติ รวดเร็วต่อการค้นหา และมีประสิทธิภาพสูงเมื่อนำไปเป็น Foreign Key |
| `name`         | TEXT                 | NOT NULL                  | ชื่อ-นามสกุลเป็นข้อมูลสำคัญในการระบุตัวตน จึงไม่อนุญาตให้เป็นค่าว่าง                                              |
| `department`   | TEXT                 | NOT NULL                  | ใช้จำแนกคณะ/ภาควิชาของผู้ใช้เพื่อการประสานงานและการสรุปสถิติ                                                             |
| `email`        | TEXT                 | NOT NULL UNIQUE           | ใช้อีเมลเป็นช่องทางติดต่อกลับ และกำหนด`UNIQUE` เพื่อป้องกันการสมัครซ้ำซ้อนของผู้ใช้คนเดียวกัน    |

### ตาราง `requests`


| คอลัมน์ | ชนิดข้อมูล | Constraints                                                                                                                         | เหตุผลที่เลือกแบบนั้น                                                                                                                                                     |
| :------------- | :------------------- | :---------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`           | TEXT                 | PRIMARY KEY                                                                                                                         | ใช้รหัสรูปแบบ Business Key (เช่น`REQ-001`) เพื่อให้อ่านง่าย สื่อความหมาย และนำไปใช้สื่อสารกับผู้แจ้งได้ชัดเจน |

| `location`     | TEXT                 | NOT NULL                                                                                                                            | สถานที่เกิดปัญหาเป็นข้อมูลบังคับ เพื่อให้เจ้าหน้าที่เข้าดำเนินการได้ถูกจุด                                            |
| `details`      | TEXT                 | NOT NULL                                                                                                                            | รายละเอียดของปัญหาต้องมีเสมอเพื่อการวิเคราะห์และแก้ไข                                                                                     |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

### 1. ทำไม `users.id` กับ `requests.id` ใช้ชนิดต่างกัน

* **`users.id` :** เป็นคีย์ที่ใช้สำหรับอ้างอิงภายในระบบฐานข้อมูล ตัวเลขจำนวนเต็มช่วยให้การทำดัชนี และการ `JOIN` ข้ามตารางมีประสิทธิภาพสูงสุดและใช้หน่วยความจำน้อย
* **`ส่วน requests.id`:** เป็นรหัสที่ผู้ใช้งานต้องพบเห็นโดยตรง เช่น `REQ-001`, `REQ-002` การมีตัวอักษรนำหน้าช่วยให้ผู้ใช้งานและเจ้าหน้าที่แยกแยะได้ทันทีว่าเป็นรหัสคำร้อง และหลีกเลี่ยงความสับสนกับการจำสลับกับรหัสตัวเลขอื่นๆ

### 2. ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูลอยู่แล้ว

* **หลักการ Defense in Depth :** การตรวจสอบข้อมูลที่ API ชั้นเดียวไม่เพียงพอ เพราะในสภาพแวดล้อมจริง ฐานข้อมูลอาจถูกเข้าถึงหรือปรับแก้ได้จากหลายช่องทาง

## 5. ตัวอย่างการใช้ JOIN

### คำสั่ง SQL

ดึงรหัสคำร้อง, ชื่อผู้แจ้ง, ประเภท, สถานที่ และสถานะ โดยทำการเชื่อมตาราง `requests` เข้ากับ `users`:

```sql
SELECT 
    r.id, 
    u.name, 
    r.request_type, 
    r.location, 
    r.status 
FROM requests r 
JOIN users u ON u.id = r.requester_id 
ORDER BY r.id 
LIMIT 5;
```

### ผลลัพธ์ที่ได้

```text
  id         name          request_type        location         status
-------  ------------  ------------------  ----------------  -----------
REQ-001  สมชาย ใจดี     แจ้งซ่อม             ห้องปฏิบัติการ 301  pending
REQ-002  สุภาวดี รักเรียน  บริการบัญชีผู้ใช้        อาคารวิศวกรรม     in-progress
REQ-003  ธนกฤต ตั้งใจ    ขอใช้อุปกรณ์          ห้องประชุม 2       completed
REQ-004  สมชาย ใจดี     แจ้งซ่อม             ห้องปฏิบัติการ 302  pending
REQ-005  ปรียา ขยันยิ่ง    อื่น ๆ               ห้องสมุด ชั้น 2      pending
```

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

เมื่อเปรียบเทียบผลลัพธ์ของ SQL `JOIN` กับโครงสร้างข้อมูล JSON ที่ API ส่งให้ React ใน Week 07:

```sql
REQ-001 | สมชาย ใจดี | แจ้งซ่อม | ห้องปฏิบัติการ 301 | pending
```

```json
{
  "id": "REQ-001",
  "requesterName": "สมชาย ใจดี",
  "requestType": "แจ้งซ่อม",
  "location": "ห้องปฏิบัติการ 301",
  "status": "pending"
}
```

### ข้อสังเกตและการเชื่อมโยง:

1. **โครงสร้างผลลัพธ์ตรงกับ Frontend ทันที:** คำสั่ง `JOIN` ทำหน้าที่รวมข้อมูลที่กระจายอยู่ 2 ตาราง (`requests` + `users`) กลับมาเป็นข้อมูลแบนราบ 1 แถวต่อ 1 คำร้อง ซึ่งมีโครงสร้างตรงกับที่ React Frontend เคยใช้งานใน Week 07 พอดี
2. **บทบาทของ Backend ใน Week 10:** ในสัปดาห์ถัดไป เมื่อเราเขียน Node.js API เชื่อมต่อกับ SQLite เราไม่จำเป็นต้องเขียนโค้ดซับซ้อนใน JavaScript เพื่อจับคู่ข้อมูลเอง เพียงแค่รันคำสั่ง `JOIN` ในฐานข้อมูล แล้วนำผลลัพธ์แถวนั้นมา map เป็น JSON ส่งออกไปให้ React ได้ทันที สะดวกและมีประสิทธิภาพสูงกว่ามาก
